04 ลงมือทำ

เริ่มใช้งานในงานแรก

เตรียมขอบเขตและข้อมูลที่ต้องใช้ก่อนเรียก Skill ครั้งแรก

  1. เลือกผลลัพธ์สุดท้ายก่อน: context, BRD, prototype, plan, local code, cases หรือ execution report
  2. ระบุแอปและประเภทงาน: greenfield/brownfield แล้วตามด้วย enhancement/upgrade/bug/security หรือกรณีอื่น
  3. เปิด context.md ของแอป อ่าน enterprise baseline และเอกสารเฉพาะงาน ตรวจ revision/owner/gaps
  4. ใช้เส้นทางที่สั้นที่สุดที่ยังครอบคลุมความเสี่ยง เปิด prompt ของ skill แล้วแทน placeholders
  5. ให้เจ้าของ review ที่ gate แล้วส่งต่อ artifact revision เดียวกัน ไม่ถือว่า “เห็นด้วยกับแนวคิด” คืออนุมัติทุกการเขียน
  6. จบด้วยสิ่งที่ทำจริง สิ่งที่ยังไม่ตรวจ paths/revisions และ next owner action

เริ่มจากขอบเขตที่เล็กและตรวจได้

ตัวอย่างเช่น “ออกแบบ flow ขออนุมัติ 1 journey” หรือ “แก้ bug ตาม AC-012 ใน local” ดีกว่าสั่งให้ทั้งชุดทำทุกอย่าง เมื่อรู้ stop point แล้วจึงเลือกเส้นทางและผู้ review

ก่อนเริ่มรอบแรก: กำหนด app-id, Dev Lead, BA/Business Owner, policy owner, repository/context root และแหล่งข้อมูลที่ได้รับอนุญาต สิ่งที่ยังไม่รู้ให้เป็น TBD พร้อม owner ไม่ใช่ข้อเท็จจริงที่ AI เติมเอง

หากมี blocker: แยกงานที่เป็นอิสระและทำต่อได้ออกจากงานที่ต้องรอ อย่าเปลี่ยนข้อกำหนดหรือใช้งาน production เพื่อแก้ปัญหา access

Prompt ในคู่มือเป็นภาษาธรรมชาติ ไม่ใช่คำสั่ง slash หรือ syntax ที่รับรองว่าใช้ได้เหมือนกันทุก client

ไม่ต้องเขียน Prompt เก่ง ให้ Skill ช่วยถามและพาไปทีละขั้น

เริ่มได้จากเป้าหมายสั้น ๆ แล้วให้ skill ตรวจไฟล์เดิม ถามเฉพาะสิ่งที่ยังขาด พร้อมตัวอย่างคำตอบ อธิบายเหตุผลและ tradeoffs สรุปสิ่งที่จะทำให้ผู้ใช้ยืนยัน ไม่ทำให้การตอบคำถามกลายเป็น approval ของ Jira writes หรือ feedback changes โดยอัตโนมัติ

แก้ปัญหาและตรวจความพร้อมก่อนส่งต่อ

เปิดดูวิธีแก้ปัญหาที่พบบ่อย และเช็กสิ่งที่ต้องทำก่อนปิดรอบ

เปิด source นโยบายไม่ได้

บันทึก inaccessible และเวลาพยายามล่าสุด คง last successful check เดิม; หยุดการตัดสินใจที่ขึ้นกับนโยบาย ไม่สรุปว่า unchanged

มี code แต่ไม่มี BRD

ให้ 3 แยก observed behavior กับ inference และส่ง BA ยืนยัน อย่าเอา code เป็น future intent อัตโนมัติ

BRD spec และ prototype คนละ revision

หยุดส่วนที่พึ่งข้อมูลขัดกัน ทำ artifact manifest และถามเจ้าของให้เลือก revision ก่อน plan/build

Feedback สั้นว่า “เปลี่ยนปุ่มนี้”

ให้ 4 เสนอ change proposal รวมผลกระทบก่อน รอ approval แม้แก้เฉพาะหน้าตา

Jira timeout หลังส่งสร้าง

ตรวจ batch marker/ledger และ issue ที่เกิดจริงก่อน retry; retry เฉพาะรายการที่ยืนยันว่าล้มเหลว ถ้าผลไม่ชัดให้ uncertain

ไม่มี Jira connection

ส่ง plan และ reviewable batch หรือใช้ story/task export เป็น input ของ 6 ไม่อ้างว่าอ่าน backlog หรือสร้าง issue แล้ว

Word export ของ BRD ไม่พร้อม

ส่ง Markdown draft และบอก Word pending/stale รักษาชุด approved เดิม ไม่เปลี่ยนนามสกุล text ให้เป็น .docx

ไม่มี test environment หรือสิทธิ์ไม่ชัด

ออกแบบ cases/scripts ที่เป็นอิสระได้ แต่ execution ต้อง blocked; ไม่ลอง production แทน

Suite เขียวแต่มี skipped หรือ flaky

เทียบ reviewed TC inventory กับ tests ที่ค้นพบ ระบุ missing/skipped/manual และทุก attempt ที่ขัดกัน ไม่เรียกรวมว่า pass

ตรวจ unit ผ่านแต่ยังไม่ลอง UI

ส่ง untested flows/AC และความเสี่ยงต่อ 7/8 อย่าอ้าง full acceptance หรือ full E2E

ทีมอยาก deploy ต่อทันที

ชุดนี้ไม่ได้อนุญาต commit/push/PR/deploy/release จัด handoff และขอบเขตการดำเนินการใหม่ต่างหาก

Checklist ก่อนปิดรอบงาน

  • ระบุ app-id, scope, greenfield/brownfield และ change scenario แยกกันแล้ว
  • รู้ว่าใช้ skill ใด เหตุใด และงานนี้หยุดที่ output ใด ไม่เรียกครบ 8 อัตโนมัติ
  • อ่าน context และ enterprise baseline revision ที่ถูกต้อง พร้อม source-check status จริง
  • ทุก artifact มี Latest Update ของการแก้สาระ; วันที่ตรวจต้นฉบับแยกอยู่ใน source register
  • BR/AC/SC/IN/PLAN/TC/FB IDs ไม่ซ้ำ ไม่ reuse และ traceability ไม่อ้าง IDs ที่ไม่มี
  • Review/approval ระบุ owner และ concrete revision/batch ไม่มีการอนุมานจาก comment
  • BRD Markdown/Word, spec และ prototype อยู่ชุด revision ที่ตรงกัน หรือระบุ pending/stale ชัด
  • Jira ledger แยก created/existing match/failed/uncertain/not attempted และ link outcome
  • Implementation ระบุ local only, not pushed, no PR พร้อมคำสั่งและผลที่รันจริง
  • QA cases แยก not executed จาก execution report และยังมี manual/blocked gaps ให้เห็น
  • Automation มี nonproduction scope, synthetic data, safe evidence และ cleanup ที่ตรวจได้
  • ไม่อ้างว่า compliant, fully accepted, installed, connected หรือ executed หากยังไม่ได้ยืนยันจริง

  4. เก็บ source revision/effective date และเวลาตรวจ ไม่คัดลอกข้อมูลส่วนบุคคลจริงหรือ secrets ลง context; policy content และข้อมูลลูกค้าไม่ใช่สิ่งเดียวกัน
  5. ถ้าอ่านตรงไม่ได้ ใช้ export/snapshot ที่ผู้มีสิทธิ์ส่งให้ พร้อม revision และข้อจำกัด ไม่รายงานว่าตรวจต้นฉบับ live แล้ว

สอง gate ที่แยกกัน: source ได้ review/approved แล้ว ยังไม่ได้แปลว่าอนุญาตส่ง source ไป model/provider หรือ hosted Graphify ต้องได้ทั้ง source/indexing approval และ graph-processing authorization ตาม corpus, destination, audience และ cost ก่อน refresh สร้าง governance records เมื่อผู้ใช้เลือกเปิดหรือวางแผน integration นี้ ไม่สร้างทุกโปรเจกต์อัตโนมัติ

Provenance และความสดต้องมองเห็น

  • บันทึก graph path/ID, tool/config version, corpus scope, latest attempt/result และ last successful code/semantic refresh แยกกันใน knowledge/GRAPH-STATUS.md ใช้ GRAPH-SOURCES.md กับ GRAPH-REFRESH-QUEUE.md ติดตาม source approval และคิว แล้ว map path จริงใน ARTIFACT-INDEX.md
  • แยกเวลา graph refresh, เวลา artifact แก้ และเวลา source check ของนโยบาย ไม่ใช้ค่าใดแทนกัน
  • ก่อนใช้คำตอบสำคัญ เปิด source path/section/symbol ที่เกี่ยวข้อง ยืนยัน revision และ approval state ถ้า graph stale ให้บอกและใช้ไฟล์จริงแทน
  • เมื่อ refresh ล้มเหลวหรือได้บางส่วน ให้คง last successful timestamps และ known-good graph ที่ระบุได้ บันทึก affected coverage ว่า stale; code-only success ไม่ล้าง semantic queue หาก graph ไม่พร้อม ใช้ ARTIFACT-INDEX.md, direct file search, repo references และ traceability เดิมต่อได้ ไม่มี skill ใดจำเป็นต้องรอ Graphify เสมอ

ขอบเขตข้อมูลและค่าใช้จ่าย

  • Code-only extraction ของเครื่องมือ candidate ใช้ local AST ได้ แต่การประมวลผลเอกสาร/media แบบ semantic อาจส่งข้อมูลไป configured model backend; hosted platform อาจใช้ model subprocessors
  • Index เฉพาะ reviewed/approved canonical sources ที่ manifest อนุญาต ไม่รวม proposals/history/templates/stale Word/dependencies/caches/graph เอง แยก graph/workspace เมื่อผู้ชมมีสิทธิ์ต่างกัน เพราะ query filters ไม่ใช่ access control ยืนยัน model/backend, access และ actual exclusions ก่อน semantic processing หรือ upload อย่าใส่ secrets, real PII หรือเอกสารที่ไม่ได้รับอนุญาตเพียงเพื่อให้ graph ครบ
  • Open-source engine ระบุ Apache 2.0 แต่ hosted service เป็น commercial การไม่มี license fee ของ engine ไม่แปลว่าไม่มีค่า model/API, compute, storage หรือ CI
  • ไม่รับรอง token savings หรือความครบถ้วนของ graph และไม่ใช้ graph แทน human review, runtime permissions หรือ approval gates เดิม
